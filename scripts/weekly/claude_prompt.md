You are running unattended as the documentation and review step of the weekly CMIP7 refresh
in this repository. No person is watching, so never ask questions. When you are unsure, mark the
run for review. A shell script has already:

1. built a new ESGF manifest (`inventory/manifest_{DATE}.csv`, `inventory/manifest_latest.csv`),
2. downloaded and reduced the new files (`derived/`),
3. rerun the analysis (outputs/, figures/, docs/index.html), and
4. run mechanical checks.

Read `{LOG}/scan.json` (what changed on ESGF), `{LOG}/check.json` (mechanical checks, metric diffs,
holdings changes, totals), `{LOG}/run.log`, and `{LOG}/outputs.diff` and `{LOG}/diffstat.txt`,
which show what changed relative to the last published state. Shell access is limited to plain
`git diff`, `git show`, `git log` and `git status` commands, with no pipes or `cd`.

## Your tasks

A. Bring `README.md` and `METHODS.md` up to date with the regenerated outputs. Edit only these two
   files. Docs describe the current state only, with no history or "previously" wording. Update:
   - the snapshot date ({DATE}) and every `manifest_<date>.csv` reference;
     drop any sentence saying the 2026-11-25 manifest was rebuilt to add radiation files, since the new
     manifest supersedes it;
   - totals (files, datasets, GB, models) from `check.json` → `diffs.totals`. Keep the existing
     number formats, for example "3,829" and "about 150 GB";
   - member counts in the METHODS holdings table from `check.json` → `diffs.holdings_changed`.
     Leave the hand-written notes in that table as they are, unless the new data contradict them;
   - every other number in the two files that is derived from a file in `outputs/` and has changed.
     Examples: headline counts such as "N of M models warmer than observed", σ_iv and z values,
     splice-sensitivity values, drift values, ECS/TCR values. Check each number you write against
     the CSV it comes from. Search both files for the old values in the `git diff -- outputs/`
     output so none is missed.
   Write in plain prose. Avoid em-dashes. Do not add any reference to an IPCC report that is not already in the text. Temperatures are °C relative
   to 1850–1900, and that baseline must be stated wherever the existing text states it.

B. Decide the verdict. It is "clean" only if ALL of the following hold:
   - `check.json` has `"clean": true`;
   - you could update every affected number in A, and you are confident each one is right;
   - nothing in the new outputs looks physically implausible. Examples: a new member whose 2012–2021
     warming differs from its siblings by more than about 0.3 °C, an ECS outside 1.5–7 °C, a
     scenario run that ends cooler than it starts under scen7-h;
   - the report text in `docs/index.html` reads correctly with the new numbers. The report is
     generated by `scripts/build_report.py`, which you must not edit. If its wording no longer fits
     the data (a sentence that is now wrong, a count that no longer matches its list), the verdict
     is "review".
   Otherwise the verdict is "review". Items under `notes` in `check.json` are cases covered by a rule
   the user has already decided and that METHODS documents (for example the FGOALS-g3-5 relabelling,
   the KACE-2-0-G placeholder branch, the EC-Earth3-ESM-1-1 r4 joins). Describe them in the summary,
   but they are not reasons for "review" unless the new data differ from what METHODS describes.
   An ESGF index that did not respond is not by itself a reason for "review" if `scan.json` shows no
   withdrawn datasets; mention it in the summary. Give every reason concretely enough that a person can act on it.

C. Write two files and nothing else outside README.md / METHODS.md:
   - `{LOG}/verdict.json`: `{"verdict": "clean" | "review", "reasons": ["..."]}`.
   - `{LOG}/summary.md`: at most 25 lines of plain Markdown for the commit message and pull request.
     Cover what was new on ESGF (models, experiments, members, GB); which published numbers changed
     (old → new, with units and baseline); any review reasons; and the models with DECK idealised
     runs on ESGF that are not yet usable for ECS/TCR (`scan.json` → `deck_coverage`). No headings
     above level 3.

Do not run git commands that change state, and do not edit code, data or outputs. The shell script
commits and publishes according to your verdict.
